# S5 Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every catalog site is built and served for real from the deployed API. That means the physics team's catalog, one bundle with all its masks, that bundle inside the Cloud Run image, `horizon`, `series` and `summary` switched to `real`, and proof that three cards at once stay fast and inside Cloud Run's 512 MiB.

**Architecture:**
- **No contract change.** S5 adds no endpoint and changes no model. The web track's multi-card work (`tk=` tickets, offsets, "+1 Lunar Day") already sends one request per card with its own `t0`, and the server answers those today.
- **Catalog swap without breaking tests.** Tests stop reading `catalog/sites.yaml` and read a fixture copy, so the physics team's file can replace the placeholders without touching any test. A catalog check command and a build-time coverage guard catch a bad catalog before it reaches the API.
- **Bundle shipping.** The bundle goes into the Docker image. `make deploy` first stages a checked bundle into `served-bundle/`, and the image sets `BUNDLE_DIR` to it.
- **Load check.** A small load script replays what the web app requests for up to 3 cards. It runs against the local API and against Cloud Run.

**Tech Stack:** Python 3.12, NumPy, FastAPI, Pydantic v2, PyYAML, rasterio, pytest, mypy strict; Docker on Google Cloud Run.

## Decisions this plan makes

1. **The placeholders stay as test fixtures and sample answers, not as catalog sites.** `tests/fixtures/catalog.yaml` is a copy of today's catalog. `contract/samples/sites/*.json` keep the `sample_*` ids, so the product preview still works on sample data. In the integrated preview, MSW's nearest-sample fallback covers the gap until the flip.
2. **The committed catalog must be final at G3.** The check command's `--final` flag rejects any site that is `is_placeholder: true` or whose `source_url` isn't `http://` or `https://`.
3. **Coverage guard at build time.** For each site, the finest terrain layer present must cover that site's whole near window (`map_half_width_m(lat, layer.half_width_m)` around the site). Otherwise the build fails and names the site and the file. Coarser layers keep today's cropping, because the 240 m reach is meant to run off the edges.
4. **The bundle ships inside the image.**
   - Bundles are small: about 8 MB plus about 0.13 MB per site.
   - The image is rebuilt on every deploy anyway.
   - A bucket mount would add infrastructure for no gain.
   - If no bundle is staged, the Docker build fails, so a deploy can't silently go out without one.
5. **Staging checks the bundle against the committed catalog** with `load_bundle`, the same check the API runs at startup. A mismatch fails on the laptop before Cloud Build runs, not as a crash-looping revision.
6. **Load thresholds (my call; the spec sets none for these endpoints):**
   - Warm 3-card page load (the second round, same requests): under 3.0 s wall time, and each request under 1.0 s.
   - Peak resident memory of the local API under the load: under 400 MB, which leaves 112 MiB of Cloud Run's 512 MiB for the runtime.
   - Cold start on Cloud Run is measured and recorded, not gated.
7. **Series cache only if the warm threshold fails.** Task 6 then adds an LRU over the month series. It isn't built up front, because series months cost little next to the summary, which is already cached.
8. **CSV batches for the physics team.** `engine.cli summary` and `engine.cli horizon` accept `--site all`. `--out` is then a directory, written as `<id>_summary.csv`, `<id>_h<height>.csv` or `<id>_far.csv`.

## Global Constraints

- Base path `/api/v1`. Errors are `application/problem+json` with the 8 stable codes. The API refuses to start when the bundle lacks a catalog site or has another `algo_version` (unchanged).
- Cloud Run service `clps-api`: project `clps-514710`, region `europe-west1`, `--max-instances 2 --memory 512Mi`, unauthenticated, CPU only.
- Catalog format: `docs/spikes/catalog-format.md`. Ids match `^[a-z0-9_]{1,64}$` and are unique; `lat_deg` is −90 to −84; `lon_deg` is in [0, 360).
- Landing times run from 2026-01-01T00:00Z to 2030-12-31T23:50Z. The ephemeris table covers 2025-12-31 to 2032-01-02, hourly.
- Commit messages carry no Co-Authored-By trailer, and PR descriptions no "Generated with" line. Comments only for a non-obvious *why*; no spec section references in code.
- Run `make typecheck` after each series of code changes and `make check` before each commit. `MenasimMoonV2/` is a test reference only: never imported by `engine/`, `api/` or `build/`.

## Review Focus

1. **The catalog edited after the bundle was built** (a site added or renamed). Staging must refuse with the missing ids before anything is uploaded. Pinned in Task 4: `test_stage_refuses_bundle_missing_a_catalog_site`.
2. **A stale `served-bundle/` from an earlier deploy.** Staging must replace it whole, so no file from the old bundle survives, and must leave it untouched when the new bundle is refused. Pinned in Task 4: `test_restage_replaces_old_files` and `test_refused_stage_keeps_previous`.
3. **A physics-team site near the 20 m file's edge.** The build must fail and name it, not serve coarser terrain without saying so. Pinned in Task 2: `test_build_refuses_site_outside_finest_terrain`.

5. **A 365-day mission on three cards at once.** That is 39 series months plus 3 summaries, and it must stay under the memory cap. Exercised by Task 5's request list (`test_card_requests_year_mission`) and measured in Task 6 step 3.

### Task 5: Three-card load check

**Files:**
- Create: `build/api_load.py`

**Interfaces:**
- Produces:
  - `card_requests(site: str, t0: str, days: float, panel: float = 2.0, antenna: float = 3.0) -> list[str]`: paths with query strings, in this order:
    1. the horizon at `mast=panel`
    2. the horizon at `mast=antenna`, only if it differs
    3. one series per month from `t0`'s month through the month of `t0 + days`
    4. the summary
  - Copy the query keys and their order from the web's `createApi` (`web/src/api/client.ts`), so the request strings match what the browser sends.

  - `problems(results: list[Result], wall_s: float, max_wall_s: float = 3.0, max_request_s: float = 1.0) -> list[str]`.
  - CLI: `python -m build.api_load --base URL --card SITE,T0,DAYS[,PANEL,ANTENNA] [--card …] [--rounds 2]`.
    - Up to 3 `--card` flags.

    - It prints the first summary's `version`.
    - Exit 1 if any round has a non-200 response, or if the **last** round has any problem.
