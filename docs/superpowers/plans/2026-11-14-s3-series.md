# S3 Series Implementation Plan

> **Updated 15 Nov for the physics team's `MenasimMoonV3`:** the horizon reach is computed per point, `min(200 km, √(2R|h|) + 10 km)`, with no terrain ceiling and no `HORIZON_TRUNCATED` warning; lunar longitude is east-positive in [0, 360); slope comes from the published 20 m slope map (`slope_resolution_m: 20` replaces `slope_baseline_m`). Where this plan says 300 km, a 20 km ceiling, [−180, 180) or a 240 m slope baseline, the spec (§7.2, §12.2) and the code are the reference.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve `GET /api/v1/scenario/series` from real ephemeris and real skylines. It returns a 10-minute, one-month series of Sun, Earth and Earth-station positions and terrain clearances, plus the visibility states (visible, blocked or unknown), for a panel height, an antenna height and one Earth station. The web app moves to the spec's scenario shape so that it can read the series.

**Architecture:** Contract first (build approach §5).
- The spec's scenario parameters replace the merged ones: `panel`, `antenna`, and `station=lat,lon,alt,min_el` with Houston as the default. The web app adapts on sample answers before any engine code lands.
- At build time, SpiceyPy writes an hourly ephemeris table and the Earth-rotation table into the bundle.
- At runtime, the engine is pure NumPy:
  - `engine/geometry.py`: interpolation, sky directions and the Earth station
  - `engine/visibility.py`: the disk fraction, Earth visibility and the contact rule
  - `engine/series.py`: assembles the month
- The API reads the tables from the bundle it already loads for the horizon.

**Tech Stack:** Python 3.12, NumPy, SpiceyPy (build and tests only), FastAPI, Pydantic v2, pytest, mypy strict; React + TypeScript, Vitest, Playwright, MSW.

**Spec:** `docs/superpowers/specs/2026-11-10-lunar-landing-site-navigator-design.md` (§6.3, §7.1, §7.3, §7.4 "Live status", §8.1–8.4, §9.3 "Sky view" and "Spacecraft settings", §11.1, §11.2, §11.4, §12.3 P2/P3/P10) and `docs/superpowers/specs/2026-11-14-build-approach-design.md` (§5, §6, §7, §9 row S3). ## Decisions this plan makes

1. **Heights run from 1 to 10 m in 1 cm steps** (the user, 14 Nov: "2.5 for example").
   - The bundle keeps one skyline row per whole metre. Any other height blends the two neighbouring rows linearly (`mask_at_height`); a whole metre returns its row exactly.
   - The blend is conservative. The true skyline is the highest of the terrain angles, each almost linear in observer height, so between whole metres the true value lies at or just below the blend.
   - A test measures the blend against a direct `march` at that height, on synthetic and real terrain. The tolerance is 0.01°.
   - A height finer than 1 cm (`2.555`) gets 422 `INVALID_PARAM`, so one scenario never has two URLs.
   - The horizon endpoint keeps its `mast` parameter (the user's S2 decision), but uses the same blend, so the sky view's silhouette matches the series.
2. **Station presets live in `/meta`.** The list is Houston (the default), Goldstone, Madrid and Canberra. Each has `alt_m: 0` and `min_el_deg: 0`, matching P3's default mask. The DSN coordinates are the ones already in the meta sample. Real DSN altitudes and masks are left for the physics team; nobody has verified them.
3. **A station below its mask means contact is 0, even where the terrain is unknown.** The prototype gives "unknown" in that case. Contact needs both conditions, so a known "no" settles it. The reference test skips those samples, and the S3 pull request asks the physics team to confirm.
4. **The series covers one calendar month (UTC)** at 600 s steps: `n` = days in the month × 144. It validates the whole scenario, so a bad URL fails the same way on both endpoints. It reads only `site`, `month`, `panel`, `antenna` and `station`.
5. **The table runs from 2025-12-31T00:00Z to 2032-01-02T00:00Z, hourly.** The day of margin at each end lets the 4-point interpolation reach every 10-minute step of the months 2026-01 to 2031-12. A month outside that range gets 422 `OUT_OF_TIME_RANGE`.
6. **Table rows are UTC hours.** SPICE converts each one with `naif0012.tls`. Interpolation runs in UTC seconds. No leap second is scheduled in that kernel after 2017.
7. **The ephemeris is a required part of the bundle.** A manifest without it fails startup with "rebuild the bundle". `HORIZON_ALGO_VERSION` stays "1", because the masks are unchanged.
8. **Responses are gzipped** (`GZipMiddleware`, minimum 1,000 bytes). A month is about 600 KB of JSON before compression (spec §9.3 estimates 2–4 MB for a year).
9. **The JPL Horizons answers are committed** to `tests/fixtures/horizons/`. They are a few KB each, git gives integrity, and the physics team can see them in the pull request. The comparison test still skips without the kernels.
10. **`w` keeps its 4 values** until S4 rewrites the score. The days default becomes 30 (§8.1, P4).

## Global Constraints

- Base path `/api/v1`; lat/lon in degrees, east-positive lon in [−180, 180); times ISO 8601 UTC; units in field names.
- Errors are `application/problem+json` with the 8 stable codes. Versioned GETs (`v=` present) get `Cache-Control: public, max-age=31536000, immutable`.
- Frame `MOON_ME_DE440_ME421` (never `IAU_MOON`, never the principal-axis frame). Kernels: `naif0012.tls`, `pck00011.tpc`, `de440s.bsp`, `moon_pa_de440_200625.bpc`, `moon_de440_250416.tf`, `earth_1962_260806_2126_combined.bpc`.
- Light time:
  - The Sun, and the Earth as a body that can block the Sun, use **CN+S** vectors from the Moon's center, minus the observer's position.
  - Earth visibility and Earth contact use **geometric** vectors (no correction) and the instantaneous station position.
- Table: `ephemeris.npy` float64 [rows × 9] km, with columns Sun CN+S, Earth CN+S, Earth geometric. `earth_rotation.npy` float64 [rows × 3 × 3] (ITRF93 → MOON_ME). Rows are UTC hours from the table start. Cubic (4-point Lagrange) interpolation.
- Azimuth runs clockwise from north; elevation is measured from the site's tangent plane. At the pole, north is the direction of longitude 0.
- Radii: Sun 696,000 km; Earth 6,378.1366 km (equatorial, as the prototype uses). Station ellipsoid: a = 6,378.1366 km, c = 6,356.7519 km (pck00011), the same as SPICE `georec`. Moon sphere R = 1,737,400 m.
- Observers sit at `(R + elevation_m + height) · up`. The Sun is seen from the panel; the Earth and the station from the antenna.
- Sun disk: 128 vertical strips in the small-angle sky plane. Each strip is compared with the panel skyline at its own azimuth (periodic linear interpolation of the 720 values). The Earth's disk is subtracted. Sun visible ⇔ f > 1e-10.
- Earth visibility: `earth_any` ⇔ the Earth disk's fraction above the antenna skyline is > 1e-10; `earth_whole` ⇔ it is ≥ 1 − 1e-10.
- Contact: the direction to the station is above the antenna skyline at its azimuth, **and** the station sees the antenna at or above `min_el_deg`.
- `sun_vis_el = sun_el + sun_radius`. `earth_vis_el = station_el` while the station is up, otherwise +90.
- Unknown (a skyline value NaN where it is read) gives `null` in JSON, never 0 and never a `NaN` token.
- Scenario parameters:
  - `panel` and `antenna` (and the horizon's `mast`): 1–10 m, at most 2 decimals; defaults 2 and 3; written without trailing zeros (`2.5`, not `2.50`)
  - `station`: lat −90–90, lon −180–180, alt −500–9,000 m, min_el 0–45°
  - `days`: 1–365, default 30
  - `t0` on the 10-minute grid
- Commit messages carry no Co-Authored-By trailer, and PR descriptions no "Generated with" line. Comments only for a non-obvious *why*; no spec section references in code.
- Run `make typecheck` after each series of code changes and `make check` before each commit. `MenasimMoonV2/` is a test reference only: never imported by `engine/`, `api/` or `build/`.

## Review Focus

1. **Months at the table's edges, and odd months:** `2026-01` and `2031-12` work; `2025-12` and `2032-01` give 422 `OUT_OF_TIME_RANGE`; `2028-02` has n = 4,176; `2027-13` gives 422 `INVALID_PARAM`. Task 6 test.
2. **Unknown skyline directions under the Sun's disk:** `sun_lit_frac` is `null`, never 0. A tiny positive fraction is never rounded to 0 in the JSON, because the web app reads `> 0` as "visible". Tasks 5 and 6 tests.
3. **Disk strips that cross azimuth 0/360, and a site at the pole (lat −90):** the same result as the same sky rotated by 180°, and finite azimuths at the pole. Tasks 3 and 5 tests.
4. **Station below its mask while the antenna skyline is unknown:** contact is 0, and `earth_vis_el` is 90. Task 5 test.
5. **Malformed station or height parameters** (`station=1,2,3`, `station=abc`, `station=95,0,0,0`, `station=0,0,0,50`, `panel=2.555`, `panel=0.99`, `antenna=10.01`, `panel=`): 422 `INVALID_PARAM` `problem+json`, never 500. Meanwhile `panel=2.5` and `antenna=2.55` are accepted. Task 1 test.
