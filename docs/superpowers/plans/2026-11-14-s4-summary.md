# S4 Summary Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve `GET /api/v1/scenario/summary` from real series. It returns the mission metrics over [landing − margin, landing + days], the verdict chips, the physics team's V2 score (7 grades, hard gates, every setting user-configurable), the windows, the daily values and one warnings list. The web app moves to that shape and gets the score box, the warnings strip and the score settings panel.

**Architecture:** Contract first (build approach §5).
- The scenario gains the score settings (`w` with 7 weights, `sun_req`, `slope`, `psr`, `margin`, `colors`). Their defaults, ranges and labels live in `config/score.yaml`; the chip thresholds in `config/rag.yaml`; the warning texts in `config/warnings.yaml`. `/meta` publishes all three.
- The engine stays pure NumPy:
  - `engine/metrics.py`: the mission window, day bins, tri-state metrics and windows, from S3's `SeriesArrays`
  - `engine/score.py`: the dust index, raw grades, the score over arrays, and one site's breakdown
- The API computes the series over the window once per (site, time, heights, station, margin) and caches the metrics, so a settings change only rescores. Text (chip reasons, warnings, the explanation) is filled in the API from the config files.

**Tech Stack:** Python 3.12, NumPy, FastAPI, Pydantic v2, PyYAML, pytest, mypy strict; React + TypeScript, zod, Vitest, Playwright, MSW.

## Decisions this plan makes

1. **Window steps.** The window starts at `t0 − margin` and has `n = margin × 6 + round_half_up(days × 144)` steps of 600 s. So a 29.53-day mission ends at the nearest 10-minute step (3.2 min early). Each step's state holds for its 600 s. Day bins are 144 steps from the window start; the last bin may be shorter and weighs by its step count. With 144-step bins, L "averaged per day then over the days" equals the plain mean of `sun_lit_frac` over the window, and C equals `dte_pct / 100`; a test checks both.
2. **Landing times are 2026-01-01T00:00Z to 2030-12-31T23:50Z** (P4). Outside: 422 `OUT_OF_TIME_RANGE`. A calendar-impossible `t0` (`2027-02-30T00:00Z`) is 422 `INVALID_PARAM`. The ephemeris table starts 2025-12-31T00:00Z, so a landing in the first day of 2026 with a margin over 23 h gets 422 `OUT_OF_TIME_RANGE` naming the earliest window start. The table is not rebuilt for this.
3. **Unknown time** (a NaN state):
   - makes `sun_pct`, `dte_pct`, `both_pct`, `earth_any_pct`, `earth_whole_pct`, `sun_disk_mean`, `contact_mean` and that day's daily values `null`
   - breaks dark and no-contact runs (it is not darkness)
   - `first_sun_h` is `null` when step 0 is unknown, or when the lit run from step 0 ends at an unknown step
   - `first_dark_after_landing_h` is `null` when an unknown step comes before the first dark step after landing; with no dark step at all it is the hours from landing to the window end
   - `both` is 1 where both are 1, 0 where either is 0, unknown otherwise
4. **"Flagged if it continues past the edges":** `longest_dark_at_edge` and `longest_no_contact_at_edge` are true when the longest run touches step 0 or step n − 1. The engine computes nothing outside the window.
5. **PSR:** `Site.in_psr: bool | None = None`, from the catalog. Every catalog site is `null` until the PSR map is in the build, so every summary carries `PSR_UNKNOWN` (info) while `psr=1`. With `psr=0` the gate and the warning are both off.
6. **Gate warnings have codes:** `EXCLUDED_PSR` and `EXCLUDED_SLOPE`, severity `blocking`, affects `score`. An excluded site names no deciding factor (the prototype's rule).
7. **`SPARSE_MEASUREMENTS` and `EFFECTIVE_RESOLUTION` are catalogued but never emitted** in S4: the build doesn't read the LDEC/EFFRES layers yet. `DEM_GAPS`, `HORIZON_TRUNCATED` and `UNCERTAINTY_UNAVAILABLE` come from the bundle's per-site list. `EARTH_ORIENTATION_PREDICTED` is added when the window ends after 2026-08-06T00:00Z.
8. **Slope scale with good == bad** (allowed: "good ≤ bad") is a step: S = 1 at or below `good`, else 0. The prototype refuses that case; we don't divide by zero.
9. **The score value is rounded to 0.1 before its color is chosen,** so a box that reads 70.0 is green. Deciding-factor ties use |Δ| ≤ 1e-9 on unrounded penalties; when the largest penalty is ≤ 1e-10, `deciding` is empty and the explanation says no grade lost points.
10. **Canonical numbers in URLs** are the shortest form (`format(v, "g")` in Python, `String(Number(v.toFixed(2)))` in TypeScript): `w=0.25,0.25,0.15,0.15,0.1,0.1,0`. The server accepts any equal spelling. The app URL writes settings only when they differ from the defaults; the API query always writes all of them.
11. **Rescoring is cached:** the API keeps the last 128 metric sets in an LRU keyed by (site, t0, days, margin, panel, antenna, station). Weights, `sun_req`, `slope`, `psr` and `colors` are not in the key.
12. **The mock layer ports the score formula** (`web/src/api/mocks/score.ts`) so the settings panel works on sample data. A Python test recomputes each committed summary sample's score with the engine and fails if the two drift.
13. **Old 4-weight links:** the server answers 422 `INVALID_PARAM`; the web codec turns an old `w` into the defaults.
14. Uncertainty (Should), insights (Should) and power (Could) stay out of the summary model until their slices.

## Global Constraints

- Base path `/api/v1`; lat/lon in degrees, east-positive lon in [−180, 180); times ISO 8601 UTC, written `YYYY-MM-DDTHH:MMZ`; units in field names.
- Errors are `application/problem+json` with the 8 stable codes. Versioned GETs (`v=` present) get `Cache-Control: public, max-age=31536000, immutable`.
- Scenario parameters, all validated by both scenario endpoints (S3 Decision 4), refused with 422 `INVALID_PARAM` naming the parameter:
  - `w`: 7 values L, C, DK, OT, LS, S, D; each 0–1 on 0.05 steps; at least one > 0; default `0.25,0.25,0.15,0.15,0.1,0.1,0`
  - `sun_req`: 0–72 h, step 0.5, default 6
  - `slope`: `good,bad,max`, each 0–90°, step 0.5, `good ≤ bad`; default `0,15,15`
  - `psr`: `0` or `1`, default `1`
  - `margin`: whole hours 0–48, default 12
  - `colors`: `green,amber`, whole numbers 0–100, `amber ≤ green`; default `70,40`
  - unchanged from S3: `panel`, `antenna` 1–10 m in 0.01 m steps (defaults 2, 3); `station` (Houston default); `days` 1–365 (default 30); `t0` on the 10-minute grid
- Weight presets: Default `0.25,0.25,0.15,0.15,0.10,0.10,0`; Sunlight first `0.60,0.20,0,0,0,0.10,0.10`.
- Grades (0 bad – 1 good):
  - L = `sun_disk_mean`
  - C = `contact_mean`
  - DK = `1 − longest_dark_h / window_h`
  - OT = `1 − longest_no_contact_h / window_h`
  - LS = 1 if `first_sun_h ≥ sun_req` else 0
  - S = `clip((bad − slope) / (bad − good), 0, 1)` (Decision 8 when equal)
  - D = `1 − dust_index`
- `score = 100 × Σ w·grade / Σ w`; each grade loses `100 × w / Σw × (1 − grade)`. A null grade with w > 0 counts 0 and adds `NULL_GRADE:<name>`; with w = 0 it raises nothing.
- Gates: `in_psr` true and `psr=1` → every grade 0, score 0, `excluded_reason: "psr"`. `slope_deg > max` → score 0, grades keep their values, `excluded_reason: "slope"`. Both → `"psr"`. Unknown slope never trips the gate.
- Score colors: green ≥ `green`, amber ≥ `amber`, red below; `excluded` otherwise. Chip thresholds (P6, interim): percentages green ≥ 60, amber ≥ 30; slope green ≤ 5°, amber ≤ 10°, red above; chip color `unknown` when the value is null.
- Dust: `D(x, y) = clip(0.5 + mean_k sin(x/L·cos a_k + y/L·sin a_k + p_k) / 2, 0, 1)`, 6 waves, L = 5,000 m, `a` then `p` drawn by `np.random.default_rng(42).uniform(0, 2π, 6)`; x, y from `engine.terrain.project`. Labeled "simulated" everywhere.
- Warnings are `{code, text, severity, affects}`; severity `info | caution | blocking`; affects `score | sun | contact | skyline | slope | all`. Lists are sorted blocking, caution, info, then catalog order.
- `status` is `"illustrative"`, and the UI says next to the score that the weights and thresholds are illustrative, not validated landing criteria.
- Commit messages carry no Co-Authored-By trailer, and PR descriptions no "Generated with" line. Comments only for a non-obvious *why*; no spec section references in code.
- Run `make typecheck` after each series of code changes and `make check` before each commit. `MenasimMoonV2/` is a test reference only: never imported by `engine/`, `api/` or `build/`.
